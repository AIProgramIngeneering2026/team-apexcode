# Проверка контракта колодой

Мы прошли по контракту Notify картами К1–К10 ([колода](p2_poker/README.md#колода)). В колоде и в задании используются общие термины, у нас они называются так: Job — `Notification`, Tool — `Channel`, `running` — `sending`, `POST /jobs` — `POST /notifications`.

Ссылки ведут на документы проекта:

- [openapi.yaml](api/openapi.yaml) — контракт API;
- [state-machine.md](state-machine.md) — жизненный цикл и запрещённые переходы;
- [tool-contract.md](tool-contract.md) — контракт канала;
- [requirements.md](requirements.md) — сценарии S1–S6 и критерии приёмки;
- [ADR-0001](adr/0001-background-worker.md) — фоновый воркер, [ADR-0002](adr/0002-idempotency-key-storage.md) — ключ идемпотентности, [ADR-0003](adr/0003-no-authentication.md) — без аутентификации.

| Карта | Ответ контракта |
|---|---|
| К1 Двойной клик | Создаётся ровно одно уведомление: оба запроса делают `INSERT`, уникальное ограничение на `idempotency_key` пропускает один. Первый получает `201`, второй `200` с тем же `id` — [ADR-0002](adr/0002-idempotency-key-storage.md) п. 5–6, [S2](requirements.md), `openapi.yaml`, `POST /notifications` (`201`, `200`). Другое тело при том же ключе — `409 idempotency_key_conflict` |
| К2 Ответ потерялся | Клиент не знает `id`, поэтому повторяет запрос с тем же `Idempotency-Key` и получает `200` с прежним `id` и текущим состоянием, новое уведомление не создаётся и отправка не запускается заново — [ADR-0002](adr/0002-idempotency-key-storage.md) п. 5, 8. Таймаут клиента маловероятен, потому что `201` возвращается до отправки, канал вызывает воркер — [ADR-0001](adr/0001-background-worker.md) п. 1 и «Рассмотренные альтернативы» A |
| К3 Неизвестная операция | Операция в Notify — выбор канала. Неизвестный канал: `422 unknown_channel`, в `details` имя канала и список доступных, ничего не сохраняется — `openapi.yaml`, ответ `ValidationError`, [S5](requirements.md), `UnknownChannel` в [tool-contract.md](tool-contract.md) («Какими ошибками Tool отказывает»). Неизвестный путь — `404 not_found` в том же формате, `openapi.yaml`, `info.description` |
| К4 Кривые параметры | Нет поля, неверный тип, недопустимое значение, пустой или слишком длинный `recipient` и `message`: `422 invalid_params`, `details.fields` содержит поле и проблему (`field`, `problem`) — `openapi.yaml`, схемы `Error`, `FieldProblem`, [tool-contract.md](tool-contract.md) («Кто проверяет параметры», `validate`), [S5](requirements.md). Не JSON — `400 bad_request`, нет заголовка ключа — `400 missing_idempotency_key`. Ничего не сохраняется |
| К5 Воскрешение | Запрещено: `delivered`, `failed`, `cancelled` — конечные, выхода из них нет, эндпоинта повтора нет — [state-machine.md](state-machine.md) («Запрещённые переходы», абзац про К5), `openapi.yaml`, `POST /notifications/{id}/cancel` (`409`). Повторить сообщение можно только новым запросом с **новым** ключом, это новый Job; прежний результат и история попыток остаются. Запрос с тем же ключом вернёт прежнее уведомление — [ADR-0002](adr/0002-idempotency-key-storage.md) п. 8 |
| К6 Отмена | Отменить можно только из `accepted`, пока воркер не взял уведомление. Из `sending` и конечных состояний — `409 invalid_transition`, состояние не меняется; частично выполненной работы, которую пришлось бы откатывать, нет, потому что отправка из `sending` не прерывается — [state-machine.md](state-machine.md) («Попытки из API»), `openapi.yaml`, `POST /notifications/{id}/cancel`, [S3](requirements.md). Одновременная отмена и захват воркером решаются условным `UPDATE`, применяется ровно одна операция — [state-machine.md](state-machine.md) («Конкурентные переходы»), [ADR-0001](adr/0001-background-worker.md) п. 3 |
| К7 Огромный вход | Тело больше 64 КиБ (лимит рассчитан на `message` в 4096 символов с худшим экранированием `\uXXXX`) — `413 payload_too_large` до разбора JSON; `message` больше 4096 символов, `recipient` больше 2048, ключ больше 255 — `422 invalid_params`; страница списка не больше 200 записей — `openapi.yaml`, `POST /notifications` (`413`, `maxLength`), `GET /notifications` (`limit`), [S5](requirements.md). Ответ получателя читается не более 64 КиБ и отбрасывается, превышение — `bad_response` — [tool-contract.md](tool-contract.md) («Tool 2: `WebhookChannel`») |
| К8 Чужой или несуществующий id | Несуществующий `id` и `id` неверного формата дают одинаковый `404 not_found`, из ответа не видно, что именно не так — `openapi.yaml`, параметр `NotificationId`, [S3, S4](requirements.md). Идентификаторы — UUID, перебором по порядку не находятся. В историю попыток не попадают тела ответов получателей — [tool-contract.md](tool-contract.md) («Что Tool возвращает»). Разделения клиентов нет, все видят все уведомления: **сознательно не закрываем**, причины и условия пересмотра в [ADR-0003](adr/0003-no-authentication.md) |
| К9 Перезапуск сервера | Уведомление в `sending` не остаётся там навсегда: при старте и каждые 30 с восстановление переводит `sending` старше 60 с в `failed` с причиной `interrupted`, клиент видит её в `failure_reason`. Уведомления в `accepted` не теряются, воркер подбирает их после старта — [ADR-0001](adr/0001-background-worker.md) п. 7 и «Цена решения», [state-machine.md](state-machine.md) («Перезапуск»), [S6](requirements.md), `openapi.yaml`, схема `FailureReason`. Дубль у получателя возможен, он отсекается по `X-Notification-Id` |
| К10 Внешний сервис | Молчание: 3 попытки по 5 с с паузами по 1 с, до 17 с, затем `failed` с причиной `timeout`. Мусор или обрыв соединения: `bad_response`; `5xx`: `receiver_error`; `4xx` и `3xx`: `rejected_by_receiver` без повторов. Тело ответа получателя не разбирается и не сохраняется, поэтому переименованное поле в ответе ни на что не влияет — [tool-contract.md](tool-contract.md) («Tool 2: `WebhookChannel`», таблица классификации), [state-machine.md](state-machine.md) («Причины `failed`»), [S6](requirements.md). Клиент видит `failed`, причину и историю попыток в `GET /notifications/{id}`, запросы клиента к API не получают `5xx` — `openapi.yaml`, схемы `NotificationDetail`, `Attempt` |
