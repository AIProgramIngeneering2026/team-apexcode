# Проверка контракта колодой

Мы прошли по контракту Notify картами К1–К10 ([колода](p2_poker/README.md#колода)). В колоде и в задании используются общие термины, у нас они называются так: Job — `Notification`, Tool — `Channel`, `running` — `sending`, `POST /jobs` — `POST /notifications`.

Ссылки ведут на документы проекта:

- [openapi.yaml](api/openapi.yaml) — контракт API;
- [state-machine.md](state-machine.md) — жизненный цикл и запрещённые переходы;
- [tool-contract.md](tool-contract.md) — контракт канала;
- [requirements.md](requirements.md) — сценарии S1–S6 и критерии приёмки;
- [ADR-0001](adr/0001-background-worker.md) — фоновый воркер, [ADR-0002](adr/0002-idempotency-key-storage.md) — ключ идемпотентности, [ADR-0003](adr/0003-no-authentication.md) — без аутентификации.

### Находки и наши решения

**1. Корректное сообщение отвергается как «огромный вход».**
*Условия.* Клиент отправляет `message` из 4096 символов кириллицы или с эмодзи. Многие клиенты (например, Python `json.dumps` по умолчанию) записывают не-ASCII как `\uXXXX`: 6 байт на символ, для символов вне базовой плоскости 12. Тело получается 24–48 КиБ.
*Что пойдёт не так.* Контракт одновременно разрешает `message` до 4096 символов (`openapi.yaml`, S5, `tool-contract.md`) и отвечает `413` на тело больше 16 КиБ. Допустимое по полям сообщение отклоняется ошибкой про размер тела, и клиент не понимает почему.
*Что должна делать система.* Лимит тела должен вычисляться от максимума полей с учётом худшего экранирования.

*Решение:* **принято.** Лимит тела поднят до 64 КиБ (худший случай около 48 КиБ на `message`, плюс `recipient` до 2048 и служебные поля). Длина `message` считается в символах Unicode. Изменено: `openapi.yaml` (ответ `PayloadTooLarge`, описание `message`), `requirements.md` (S5: новый лимит и критерий на 4096 символов Unicode), `tool-contract.md` (символы, не байты), К7 в этом файле.

**2. Канал сохранённого уведомления пропал из `Registry`.**
*Условия.* В `accepted` лежит уведомление с `channel = telegram`. До того, как воркер его взял, приложение перезапустили с конфигурацией без токена Telegram, и канал не зарегистрировался (или канал убрали из кода).
*Что пойдёт не так.* `UnknownChannel` описан только для API (`422` до сохранения, `tool-contract.md`). Что делает `Dispatcher`, когда `Registry.get` бросает его уже в воркере после захвата, не сказано: исключение не из «кода канала», воркер может упасть, а уведомление зависнет в `sending` и через 60 с получит `interrupted`, хотя настоящая причина другая.
*Что должна делать система.* Не вызывать канал, перевести уведомление в `failed` с понятной причиной, воркер продолжает работу.

*Решение:* **принято.** `Dispatcher` перехватывает `UnknownChannel`, ставит `failed` с причиной `internal_error` и `failure_detail = "channel not registered"`. Новую причину не вводим: список из семи значений уже согласован в четырёх документах и в OpenAPI, различие видно в `failure_detail`. Изменено: `tool-contract.md` (новая строка в таблице ошибок), `state-machine.md` (описание `internal_error`).

**3. Результат отправки не удаётся записать: БД недоступна.**
*Условия.* Воркер вызвал webhook, получатель ответил `200`. При записи результата БД не отвечает (перезапуск контейнера PostgreSQL, `database is locked` в SQLite).
*Что пойдёт не так.* ADR-0001 описывает условные переходы и восстановление после падения процесса, но не говорит, что делает живой воркер при ошибке БД. S6 требует, чтобы воркер не останавливался. Без правила возможны три плохих исхода: фоновая задача молча умирает при живом API, результат теряется без следа в логах, воркер бесконечно повторяет запись.
*Что должна делать система.* Ограниченное число повторов записи, запись в лог с `notification_id`, продолжение цикла; судьба уведомления должна быть определена.

*Решение:* **принято.** Добавлен п. 9 в ADR-0001: запись результата повторяется до 3 раз с паузой 1 с, затем ошибка в лог и переход к следующему уведомлению; цикл опроса при ошибке БД не останавливается. Уведомление остаётся в `sending` и восстановление переводит его в `failed` с причиной `interrupted`. API при недоступной БД возвращает `500 internal_error`, `/health` — `503`. В «Цену решения» добавлен ложный `failed` при сбое БД.

### Итог

Приняты все три находки. Они изменили лимит тела запроса, контракт `Dispatcher` для сохранённых уведомлений и поведение воркера при сбое БД; отклонённых нет.
