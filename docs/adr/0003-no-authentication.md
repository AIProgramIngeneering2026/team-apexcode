# ADR-0003. В первой версии API без аутентификации

- **Дата:** 2026-11-15
- **Статус:** предложено (после влития PR заменить на «принято»)
- **Связанные документы:** [README](../../README.md) (границы системы), [ADR-0002](0002-idempotency-key-storage.md), [openapi.yaml](../api/openapi.yaml)

## Контекст и ограничения

У Notify один тип клиента: разработчик или сервис, который вызывает API. Нужно решить, различает ли система клиентов и ограничивает ли им доступ.

Что известно:

- Учебный проект на два семестра, два разработчика; первый семестр заканчивается работающим прототипом, который запускается одной командой `docker compose up`.
- В границах проекта (README) нет регистрации пользователей и разграничения прав.
- Сервис запускается локально и в учебной демонстрации, в интернет не публикуется.
- Из-за отсутствия «владельца» у уведомления карта К8 («чужой или несуществующий id») формулируется иначе: чужих данных в системе нет, есть только общие.

## Решение

**В первой версии API доступен без аутентификации и авторизации. Все клиенты равноправны и видят все уведомления.**

Как это отражено в контракте:

1. Любой `id`, которого нет, включая значение неверного формата, даёт `404 not_found`. Ответ не раскрывает, чем «нет» отличается от «не такой формат».
2. Идентификаторы уведомлений — UUID, их нельзя перебрать по порядку.
3. `Idempotency-Key` глобален (см. ADR-0002): клиентам рекомендуется UUID.
4. Тела ответов получателей в API и в историю попыток не попадают (только код ответа и краткая причина). Но `recipient` хранится и возвращается в `GET /notifications` и `GET /notifications/{id}` как есть, а webhook-URL часто содержит токен (в пути или в query). Поэтому любой клиент видит адреса и токены, которые указали другие клиенты. В логах URL получателя пишется только как схема, хост и порт (S1), но в БД и в ответах API он хранится полностью.
5. Сервис не публикуется в сеть за пределами локального запуска. Это условие эксплуатации, а не защита.

## Рассмотренные альтернативы

**A. Статичный API-ключ в заголовке (`Authorization: Bearer ...`) из переменной окружения.**
Дёшево: одна проверка в middleware. Не даёт разделения клиентов, но закрывает анонимный доступ. Отвергнуто на этом этапе: сам по себе ключ не решает К8, а требует управления секретом в compose и тестах; требования проекта этого не содержат. Может быть первым шагом при публикации сервиса.

**B. Ключи по клиентам с привязкой уведомлений к владельцу (таблица клиентов, `owner_id`).**
Решает К8 полностью и делает идемпотентность ключа персональной. Отвергнуто: добавляет сущность, миграции, выдачу ключей и тесты; это отдельная функциональность, а не часть учебного ядра.

**C. OAuth / JWT с внешним провайдером.**
Стандарт для публичных API. Отвергнуто: внешняя зависимость и сложность несоразмерны задаче.

## Цена решения

- **Любой, кто достучался до порта, может создавать, читать и отменять любые уведомления.** Сервис нельзя публиковать в сеть без доработки.
- **Нет защиты от злоупотребления:** нет лимитов запросов, а сервис отправляет HTTP-запросы на адреса, которые указал клиент. Вместе с известным ограничением SSRF (README) это делает публикацию небезопасной.
- **Секреты в `recipient` видны всем клиентам.** Токен в URL получателя доступен любому, кто может читать API. Клиентам не стоит передавать в `recipient` URL с долгоживущими секретами; при добавлении аутентификации ответы должны скрывать `recipient` от чужих клиентов.
- **Нет аудита «кто создал».** Разбор инцидентов опирается на `correlation_id` и историю попыток.
- **Общий набор ключей идемпотентности:** клиенты с одинаковым ключом могут получить чужое уведомление или `409` (см. ADR-0002).

## Условия пересмотра

Решение пересматривается, если:

- сервис нужно запускать вне локальной среды или демонстрации;
- в проект добавляются пользователи или несколько клиентов с разными правами (тогда `owner_id`, ключи идемпотентности «клиент + ключ», `404` для чужого `id`);
- вводятся лимиты запросов или квоты;
- появятся получатели, чьи URL содержат секреты, которые нельзя показывать другим клиентам (тогда скрывать или маскировать `recipient` в ответах);
- во втором семестре LLM получает право отправлять уведомления от имени пользователя.
