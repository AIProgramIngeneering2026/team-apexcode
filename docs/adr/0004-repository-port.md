# ADR-0004. Порт хранилища: синхронный `NotificationRepository`, один метод — одна транзакция

- **Дата:** 2026-11-24
- **Статус:** принято
- **Связанные документы:** [ADR-0001](0001-background-worker.md), [ADR-0002](0002-idempotency-key-storage.md), [state-machine.md](../state-machine.md), [architecture.md](../architecture.md), [`domain/repository.py`](../../src/notify/domain/repository.py)

## Контекст и ограничения

Практика 4 добавляет API и хранилище. API и воркер (два участника) должны работать с хранилищем параллельно и не ждать друг друга, а ядро по требованию проекта не импортирует SQLAlchemy.

Что известно:

- `Channel.send` и `Dispatcher.process` синхронные; `WebhookChannel` ждёт ответ получателя до 17 с (ADR-0001).
- Захват, отмена и итоговый переход должны быть условными `UPDATE ... WHERE status = ...` с проверкой числа затронутых строк (ADR-0001, [state-machine.md](../state-machine.md)).
- Смена состояния и запись попыток применяются в одной транзакции (требование практики 4).
- Идемпотентное создание: один `INSERT`, без предварительного `SELECT` (ADR-0002, п. 6).
- Нужна реализация в памяти для модульных тестов API и реализация на SQLite (затем PostgreSQL).
- Таблицу разрешённых переходов знает только `Notification`.

## Решение

**Порт `NotificationRepository` (`Protocol`) лежит в `src/notify/domain/repository.py`. Он синхронный. Каждый метод выполняется в одной транзакции и не раскрывает вызывающему сессию или транзакцию.**

1. **Методы.** `create`, `get`, `attempts`, `list`, `cancel`, `list_accepted`, `claim`, `finish`, `ping`. Сигнатуры зафиксированы тестом `tests/domain/test_repository_port.py`; менять их можно только вместе с этим ADR и обеими реализациями.
2. **Условные операции.** `cancel` и `claim` — `UPDATE ... WHERE id = ? AND status = 'accepted'`, `finish` — `... AND status = 'sending'`. Ноль затронутых строк означает проигранную гонку: `claim` возвращает `None`, `finish` возвращает `False` и ничего не записывает, `cancel` перечитывает запись и бросает `InvalidTransition` (или `NotificationNotFound`).
3. **Правила переходов не дублируются.** Целевой статус и причина берутся из команд `Notification` (`cancel()`, `start()`, `deliver()`, `fail()`); хранилище лишь делает их условными на уровне БД. Запись восстанавливается из БД полным конструктором `Notification(...)`.
4. **`finish` принимает уведомление, уже переведённое `Dispatcher`.** В одной транзакции пишутся статус, причина, пояснение, `updated_at` и попытки. Номер попытки задаёт хранилище: позиция плюс один.
5. **Идемпотентность.** `create(notification, idempotency_key, request_hash)` вставляет запись; при нарушении уникальности ключа откатывает транзакцию, читает запись по ключу и сравнивает `request_hash`: совпал — `CreateResult(created=False)`, не совпал — `IdempotencyKeyConflict`.
6. **Синхронный стек.** SQLAlchemy в синхронном режиме, эндпоинты FastAPI объявлены обычными функциями (выполняются в пуле потоков), воркер обрабатывает до `WORKER_CONCURRENCY` уведомлений в потоках. Для SQLite соединения открываются с `check_same_thread=False`, `PRAGMA foreign_keys = ON` и ненулевым `busy_timeout`; режим журнала WAL разрешён.
7. **Две реализации, один контракт.** `InMemoryNotificationRepository` (`storage/memory.py`, под блокировкой) и `SqlNotificationRepository` (`storage/sql.py`) проходят одни и те же тесты `tests/storage/test_repository_contract.py` (фикстура `repo` в `tests/storage/conftest.py`).
8. **Слои.** `api` не импортирует `storage` и `worker`, репозиторий внедряется в `create_app(repo, ...)`; `storage` не импортирует `api` и `worker`. Проверяет `tests/test_architecture.py`.

## Рассмотренные альтернативы

**A. Асинхронный стек (`async def`, `AsyncSession`, `asyncpg`/`aiosqlite`).**
Лучше масштабируется на большое число соединений. Отвергнуто: `Dispatcher` и `Channel` синхронные, пришлось бы переписывать ядро и контракты каналов или оборачивать их в потоки. Для учебной нагрузки выигрыша нет.

**B. Порт отдаёт сессию или Unit of Work (`with repo.transaction() as tx: ...`).**
Гибко: вызывающий сам склеивает операции в транзакцию. Отвергнуто: транзакционная логика утекает в API и воркер, а в памяти пришлось бы эмулировать откат. Все нужные атомарные сочетания (`create`, `finish`) известны заранее и оформлены отдельными методами.

**C. Один метод `save(notification)` с обычным `UPDATE` по `id`.**
Проще интерфейс. Отвергнуто: «прочитать, изменить, записать» не защищает от гонки отмены и захвата и от записи итога поверх `interrupted` (ADR-0001, [state-machine.md](../state-machine.md)).

**D. Переходы как методы хранилища без участия `Notification` (чистый SQL).**
Один источник правды в БД. Отвергнуто: правила переходов оказались бы в двух местах, а реализация в памяти повторяла бы их вручную. Решение п. 3 оставляет единственную таблицу переходов в ядре.

## Цена решения

- **Потоки вместо `asyncio`:** число одновременных соединений ограничено размером пула потоков; для учебной нагрузки этого достаточно.
- **Каждая операция — отдельная транзакция.** Склеить в одну транзакцию, например, `claim` и `finish`, нельзя; это сознательно: между ними идёт сетевой вызов, и держать транзакцию открытой нельзя.
- **Два места с одной логикой.** Реализации в памяти и на SQL нужно держать согласованными; защита — общие контрактные тесты.
- **SQLite при многопоточной записи** может отвечать `database is locked`; смягчается `busy_timeout` и WAL, на PostgreSQL проблема исчезает.
- **Порт расширяется отдельными методами:** для восстановления зависших `sending` (практика 6, задача №14) добавится метод, например `interrupt_stale(older_than)`; он оформляется правкой этого ADR.
- **Имя метода `list` затеняет встроенный `list`** внутри класса порта; поэтому в `repository.py` включены отложенные аннотации.

## Условия пересмотра

Решение пересматривается, если:

- каналы или `Dispatcher` станут асинхронными;
- воркер выносится в отдельный процесс или запускается в нескольких экземплярах (тогда `claim` на PostgreSQL можно перевести на `SKIP LOCKED`, ADR-0001);
- потребуется атомарно менять несколько уведомлений за одну операцию;
- в запрос и таблицу добавятся поля, влияющие на `request_hash` (ADR-0002).
