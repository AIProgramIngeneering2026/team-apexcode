## Описание задач

### 1. Скелет репозитория
Структура: `src/notify/domain`, `src/notify/api`, `src/notify/channels`, `tests/`, `docs/`. Настроен менеджер зависимостей, линтер, `.gitignore`, `.env.example`.
**Готово, когда:** проект ставится по README, пустой тест запускается командой `pytest`.

### 2. Доменное ядро
Класс `Notification` с состояниями и таблицей разрешённых переходов; недопустимый переход приводит к `InvalidTransition`. Ядро не импортирует FastAPI и SQLAlchemy.
**Готово, когда:** тесты проверяют все разрешённые и все запрещённые переходы (параметризованно).

### 3. Registry и каналы
`Registry.register/get`, ошибка «неизвестный канал» (`UnknownChannel`, в ней имя канала и список доступных); `LogChannel`; `WebhookChannel` с внедряемым портом `HttpSender` (Protocol в ядре): `validate_recipient`, классификация ответов по таблице из `docs/tool-contract.md`, повторы, заголовки `X-Notification-Id` и `X-Correlation-ID`. Реальный httpx-адаптер делается в задаче №9, в тестах подставляется fake-sender. Контракт `Channel` и общие типы приходят из задачи №18.
**Готово, когда:** новый тестовый канал регистрируется без правки остального кода; тесты на неизвестный канал, неверные параметры с указанием поля у обоих каналов и классификацию ответов webhook.

### 4. S1: создание уведомления (API)
`POST /notifications` в порядке проверок из `openapi.yaml` (413 → 400 → ключ → канал → `channel.validate` → `repo.create`), `GET /channels` из `Registry`, `GET /health` по `repo.ping()`. API — тонкий слой: правил переходов и SQL в нём нет. Отправку выполняет воркер (задача №20).
**Готово, когда:** выполнены критерии приёмки S1 про создание (`201`, `id`, `status = accepted`); тест на репозитории в памяти.
### 5. S2: идемпотентность в API
Заголовок `Idempotency-Key` (формат: пустой — `400`, недопустимый — `422`), `request_hash` — SHA-256 канонического JSON `channel`, `recipient`, `message`; ответы `201` / `200` / `409 idempotency_key_conflict` (ADR-0002). Хранение ключей и уникальность — в задаче №10.
**Готово, когда:** выполнены критерии S2, есть тест на формат ключа и на то, что порядок полей и форматирование JSON не влияют на хэш.
### 6. S3: отмена в API
`POST /notifications/{id}/cancel`: вызывает `repo.cancel`, `InvalidTransition` превращается в `409`, неизвестный и неверный `id` — в `404`. Условный `UPDATE` — в задаче №10.
**Готово, когда:** выполнены критерии S3, включая `409` для всех остальных состояний; тест на гонку отмены и захвата лежит в задаче №10.
### 7. S4: просмотр
`GET /notifications/{id}` и `GET /notifications?status=`; в ответе по `id` история попыток и причина `failed`; `404` для несуществующего `id` и `id` неверного формата.
**Готово, когда:** выполнены критерии S4.

### 8. S5: валидация и ошибки
Единый формат ошибок во всём API, включая ошибки валидации FastAPI, неизвестный путь (`404`), неподдерживаемый метод (`405 method_not_allowed`), необработанные исключения (`500` без трассы и SQL) и лишние поля тела (`additionalProperties: false`, `422`). Значения из запроса в ответ не возвращаются. Middleware `X-Correlation-ID`: из запроса или сгенерированный, в заголовке ответа и в `error.correlation_id`. Коды: `unknown_channel`, `invalid_params`, `missing_idempotency_key`, `bad_request`, `payload_too_large` (тело больше 64 КиБ, проверяется до разбора JSON).
**Готово, когда:** выполнены критерии S5, каждая ошибка имеет тест.
### 9. S6: адаптер и fake
HTTP-адаптер с timeout 5 с, 2 повторами, классификацией причин (`timeout`, `rejected_by_receiver`, `receiver_error`, `bad_response`), без редиректов, лимит чтения ответа 64 КиБ, fake-получатель с режимами ответов.
**Готово, когда:** выполнены критерии S6, интеграционные тесты идут против fake.

### 10. SQL-хранилище и миграции
`SqlNotificationRepository` по порту из [ADR-0004](adr/0004-repository-port.md). Таблицы `notifications` (с `idempotency_key` UNIQUE, `request_hash`, `failure_reason`, `failure_detail`, индекс по `status` и `created_at`) и `delivery_attempts`; миграции Alembic (создания таблиц при старте нет). Один `INSERT` в `create`, условные `UPDATE` в `cancel` / `claim` / `finish`, статус и попытки в `finish` в одной транзакции.
**Готово, когда:** чистая БД поднимается миграциями, данные переживают перезапуск, контрактные тесты репозитория проходят, есть тесты на откат транзакции и на гонки (отмена и захват, одновременные `create`).
### 11. CI
Workflow запускает линтер и `pytest` на каждый PR; в тестах есть проверка, что `docs/api/openapi.yaml` совпадает с приложением (задача №22), поэтому CI проверяет и схему OpenAPI, которую генерирует FastAPI.
**Готово, когда:** на PR виден зелёный/красный статус; настроен запрет вливания при красном CI.
### 12. Диагностика
JSON-логи (URL получателя пишется только как схема, хост и порт), настройки из переменных окружения. Middleware `X-Correlation-ID` и `/health` сделаны в практике 4 (задачи №4 и №8); здесь в логи добавляется `correlation_id` и подключается JSON-формат.
**Готово, когда:** в логах одного запроса везде один `correlation_id`; `/health` отвечает `503` при недоступной БД.
### 13. Docker Compose и PostgreSQL
Сервисы `app`, `postgres`, `fake-webhook`; миграции применяются при старте.
**Готово, когда:** `docker compose up` из чистого клона поднимает рабочий сервис.

### 14. Восстановление и устойчивость воркера
При старте и каждые `RECOVERY_INTERVAL_SECONDS` уведомления в `sending` старше `SENDING_STALE_AFTER_SECONDS` переводятся в `failed` с причиной `interrupted`; для этого в порт репозитория добавляется метод (правка ADR-0004 и обеих реализаций). При ошибке БД воркер повторяет запись результата до 3 раз с паузой 1 с, пишет ошибку в лог и не останавливается.
**Готово, когда:** выполнены критерии S6 про `interrupted` и сбой БД; тесты: зависшее `sending` восстанавливается, опоздавший воркер не перезаписывает `failed`, цикл воркера переживает ошибку БД.

### 17. Dispatcher
`Dispatcher` берёт канал из `Registry`, вызывает `send`, применяет переход `sending → delivered / failed` по `ToolResult` к доменному объекту и БД не трогает; исключение канала и `UnknownChannel` при отправке превращает в `failed` с `internal_error` (`failure_detail = "channel not registered"` для пропавшего канала); воркер при этом не останавливается. Конкретных каналов не знает.
**Готово, когда:** тесты на тестовом канале-заглушке (успех, отказ с причиной, исключение канала, канал пропал из `Registry`); новый канал подключается без правки `Dispatcher`.

### 20. Воркер
`Worker(repo, dispatcher, poll_interval, concurrency)`: `run_once()` для тестов, фоновый цикл с `start()` / `stop()`. Путь: `list_accepted` → `claim` → `Dispatcher.process` → `repo.finish`. `finish` вернул `False` — предупреждение в лог. Ошибка репозитория и `InvalidTransition` цикл не останавливают. Восстановление `interrupted` и повторы записи — задача №14.
**Готово, когда:** `run_once` доводит `accepted` до `delivered` / `failed`, отменённое не отправляется, повторный `run_once` не шлёт второй раз.
