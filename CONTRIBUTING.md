# Как работать с репозиторием

Команда из двух человек. Каждая задача идёт через issue, ветку и pull request; в `main` никто не коммитит напрямую.

## Ветки

- `main` — всегда рабочая; защищена: вливание только через PR, зелёный CI и одобрение review.
- Рабочие ветки создаются от `main` и называются `<тип>/<номер-issue>-<короткое-описание>`:
  - `feature/4-create-notification` — новая функциональность;
  - `fix/12-correlation-id-missing` — исправление ошибки;
  - `docs/1-readme` — документация;
  - `test/9-adapter-timeouts` — только тесты;
  - `chore/11-ci` — инфраструктура и прочее.
- Ветки короткоживущие: одна задача — одна ветка; после вливания ветка удаляется.

## Коммиты

Формат: `<тип>: <что сделано>` в повелительном наклонении, до 72 символов в первой строке.

```
feat: add idempotent creation of notifications
fix: reject cancel for notification in sending state
test: cover invalid state transitions
docs: describe failure scenarios
chore: add CI workflow
refactor: extract http sender from webhook channel
```

Типы: `feat`, `fix`, `test`, `docs`, `chore`, `refactor`. Один коммит — одна логическая правка. Если коммит относится к issue, в теле указываем `Refs #N`.

## Pull request

1. Создаём PR из своей ветки в `main`, в описании: что сделано, `Closes #N`, как проверить, какие сценарии затронуты.
2. PR небольшой (желательно до ~300 строк изменений), одна задача на PR.
3. Перед запросом review: тесты проходят локально, CI зелёный, конфликтов с `main` нет.
4. Вливаем способом **Squash and merge**, заголовок коммита по формату выше.

## Review

- Автор не вливает свой PR; ревьюер — второй участник команды. У каждого участника за практику должны быть свой влитой PR и своё review.
- Ответ на review — в течение суток; если не успеваем, пишем об этом в PR.
- Ревьюер проверяет:
  - решение соответствует критериям приёмки из `docs/requirements.md`;
  - есть тесты (позитивные и негативные), они осмысленные;
  - доменное ядро не зависит от фреймворка и БД;
  - нет секретов, отладочного кода и мусорных файлов;
  - ошибки возвращаются в едином формате;
  - код читаем: названия, структура, комментарии там, где логика неочевидна.
- Комментарии формулируем по делу и вежливо; блокирующие замечания помечаем `blocker:`, остальные — рекомендации.
- Review оформляется в GitHub: `Approve` или `Request changes` с комментариями.

## Issues

- Каждая задача из `docs/backlog.md` — issue с исполнителем и меткой практики.
- Исполнитель сам переводит issue в работу и связывает его с PR.
- Новая проблема или идея — новый issue, а не правка «заодно».

## Definition of Done

Задача считается сделанной, когда выполнены **все** пункты:

- [ ] реализованы критерии приёмки из issue и соответствующего сценария;
- [ ] есть автотесты: позитивный и хотя бы один негативный; новые поведения покрыты;
- [ ] все тесты проходят локально и в CI, линтер без замечаний;
- [ ] PR прошёл review другого участника, замечания учтены или обсуждены;
- [ ] документация обновлена, если изменились API, сценарии, состояния или запуск (OpenAPI, README, `docs/`);
- [ ] в коде и в репозитории нет секретов, паролей и токенов (только `.env.example`);
- [ ] изменения влиты в `main` через squash, issue закрыт, ветка удалена;
- [ ] после вливания проект по-прежнему запускается по инструкции из README.
