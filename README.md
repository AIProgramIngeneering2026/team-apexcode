# Notify — сервис уведомлений

Небольшой HTTP-сервис, который принимает запросы «отправь сообщение получателю через канал X», выполняет отправку в фоне и хранит статус и историю попыток по каждому уведомлению.

## Какую проблему решает

Сервисам и скриптам, которым нужно кого-то уведомить (отправить webhook, сообщение в Telegram, запись в лог), приходится каждый раз писать свой код отправки, обработки таймаутов и повторов, и нигде не видно, дошло ли сообщение.

Notify даёт единый API:

- один запрос вместо отдельной интеграции с каждым каналом;
- понятный статус каждого уведомления: принято, отправляется, доставлено, не доставлено, отменено;
- безопасный повтор запроса (идемпотентность): если клиент не получил ответ и отправил запрос заново, сообщение не уйдёт дважды;
- история попыток доставки с причиной ошибки.

## Для кого

| Пользователь | Что ему нужно |
|---|---|
| Разработчик, интегрирующий свой сервис с Notify (основной клиент API) | Создать уведомление, узнать его статус, отменить, пока оно не отправлено |
| Получатель webhook (внешняя система) | Получить HTTP POST с сообщением и идентификатором уведомления |
| Дежурный/разработчик, разбирающий проблемы | По логам с `correlation_id` и истории попыток понять, почему уведомление не доставлено |

## Что входит в систему

- REST API с OpenAPI-контрактом: создание уведомления (с ключом идемпотентности), получение по id, список с фильтром по статусу, отмена, список каналов, health check.
- Жизненный цикл уведомления с проверкой переходов: `accepted → sending → delivered / failed`, `accepted → cancelled`.
- Каналы за единым контрактом: `log` (запись в лог), `webhook` (HTTP POST), `telegram` (по возможности).
- Адаптер внешних HTTP-вызовов: timeout, ограниченное число повторов, обработка недоступности и некорректного ответа.
- Фоновая обработка: воркер берёт принятые уведомления и отправляет их.
- Хранилище с миграциями (SQLite на прототипе, затем PostgreSQL).
- Структурированные логи с correlation ID, конфигурация из окружения.
- Автотесты и CI, запуск одной командой `docker compose up`.

## Чего в системе нет (границы)

- Пользовательского интерфейса (только API).
- Регистрации пользователей, авторизации и разграничения прав (в первой версии доступ к API без аутентификации).
- Отправки email и SMS.
- Ручного повтора неудачного уведомления (`failed` — конечное состояние).
- Шаблонов сообщений, рассылок по спискам, приоритетов и очередей на брокере (Kafka, RabbitMQ).
- Гарантии «ровно один раз» на стороне получателя: сервис обеспечивает «хотя бы один раз» и передаёт `X-Notification-Id`, чтобы получатель мог отсекать дубли.
- Защиты от обращений на внутренние адреса (SSRF) — известное ограничение учебной версии.
- Использования LLM — это второй семестр (см. ниже).

## Как устроено

```
запрос → Notification (Job) → Dispatcher → Registry → Channel (Tool) → ToolResult
```

- `Notification` — единица работы с состояниями и проверкой переходов.
- `Dispatcher` — берёт уведомление, находит канал в `Registry`, вызывает его и по результату переводит уведомление в `delivered` или `failed`; конкретных каналов не знает.
- `Registry` — соответствие «имя канала → реализация».
- `Channel` — единый контракт отправки: `send(recipient, message) → ToolResult`.

Подробные сценарии и жизненный цикл — в [docs/requirements.md](docs/requirements.md).

### Задел под LLM (второй семестр)

LLM будет принимать запрос на естественном языке («напомни Ивану в Telegram завтра про созвон»), выбирать канал из списка `GET /channels` и формулировать текст под получателя. Для этого выбор канала и составление сообщения вынесены за интерфейс, сейчас они задаются явно в запросе.
